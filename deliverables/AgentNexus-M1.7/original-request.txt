**项目：** AgentNexus v0.4  
**开发基线：** M1.6.1  
**执行代理：** Codex  
**任务性质：** 原生多 Agent 运行时集成、协作验证、自主软件研发试运行。

# 一、本轮战略目标

AgentNexus 已经完成：

- M0：主流开源 Harness 源码研究与架构设计。
- M0.1：Feature Registry、Policy、Context Archive、Audit Trail、Tool Gateway。
- M1：受限本地内核。
- M1.2：强制策略执行、精确资源授权、Operation Reconciliation。
- M1.3：Runtime Identity、Trusted IPC、ExitProof 协议。
- M1.4：Windows 执行链候选实现。
- M1.5：Production Bootstrap、Broker、Sandbox 候选实现。
- M1.5.1：CPU 根因调查与失败关闭。
- M1.6：Native Harness、Agent Loop、Message Bus、Task Scheduler、三级资源治理。
- M1.6.1：Storage Owner、Context Provenance、Message Reliability、Rules Compiler、Gate Runtime。

M1.6.1 当前状态：

- 本地 Native Harness 稳定性范围：PASS。
- 新增测试：99/99 PASS。
- 完整回归：469 PASS、8 NOT_RUN、2 FAIL。
- 严格 CPU 累计预算：BLOCKED。
- 完整生产执行链：BLOCKED。
- 真实 Provider：尚未接入。

## 本轮核心目标

**让 AgentNexus 第一次真正承担一个完整的软件研发任务，由多个不同职责的 Agent 自主协作完成，而不是仅仅展示五种 Agent 能够启动和互相发送消息。**

本轮必须验证：

1. Development Agent 能够理解项目并自主制定研发计划。
2. Development Agent 能够拆分任务。
3. 多个 Subagent 能够并行承担独立工作。
4. Subagent 能够与主 Agent 双向通信。
5. Resident Agent 能够持续接收消息并唤醒相关 Agent。
6. Background Reviewer 能够独立审查代码。
7. Coordinator 能够协调任务和共享资源。
8. Context Assembly 能够支持跨任务、跨会话的连续研发。
9. Workflow Runtime 能够真正参与研发流程。
10. Resource Governance 能够控制 Agent 的资源消耗。
11. 所有重要操作都能够追溯。
12. Agent 能够在任务失败、中断和恢复后继续工作。

本轮不要求完整产品一次性完成。

但必须产生一个真实、可复现、可审计的多 Agent 软件研发闭环。

# 四、核心工作线 A：Development Agent 自主研发能力

这是本轮最重要的部分。

Development Agent 不应该只是接收一个已经拆分好的任务，然后执行编码。

它必须具备真正的研发管理能力。

## A1. 项目理解

Development Agent 启动后：

1. 读取项目规则。
2. 读取项目需求。
3. 读取现有代码。
4. 读取架构和历史决策。
5. 分析项目状态。
6. 识别缺失功能。
7. 识别技术风险。
8. 形成研发计划。

必须保留项目规则和文件来源。

不能仅凭摘要猜测项目状态。

## A2. 自主规划

主 Agent 应能够：

- 制定项目架构。
- 识别工作模块。
- 建立任务依赖。
- 确定任务优先级。
- 估计资源需求。
- 选择合适的 Agent 类型。
- 决定哪些任务可以并行。
- 决定哪些任务必须串行。
- 制定验收标准。

任务计划必须结构化保存。

## A3. 自主任务分发

主 Agent 根据任务内容派发子 Agent。

例如：

```text
Development Agent
       |
       +---- Research Agent
       |
       +---- Architecture Agent
       |
       +---- Coding Agent A
       |
       +---- Coding Agent B
       |
       +---- Test Agent
       |
       +---- Review Agent
```

这只是示例，实际分工由主 Agent 根据任务依赖决定。

不能为了展示并行而把相互依赖的任务强行并行。

也不能把所有任务都串行执行。

## A4. 交付整合

主 Agent 必须：

- 接收子 Agent 的交付。
- 验证 Artifact。
- 检查测试结果。
- 处理接口冲突。
- 处理代码冲突。
- 处理设计分歧。
- 决定是否重新派发任务。
- 整合最终代码。

不能仅根据子 Agent 自报完成就验收。

必须检查真实文件、测试和交付证据。

# 五、核心工作线 B：Development Subagent

本轮必须验证真正的多子 Agent 协作。

子 Agent 不是简单的多个独立聊天窗口。

每个子 Agent 必须具备：

- 独立 Agent ID。
- 独立 Runtime Instance。
- 独立 Task。
- 独立 Context。
- 独立 Model Binding。
- 独立 Resource Budget。
- 明确的文件访问范围。
- 明确的工具权限。
- 明确的交付合同。

## B1. 子 Agent 类型

至少验证：

1. Research Agent。
2. Architecture Agent。
3. Coding Agent。
4. Test Agent。
5. Debug Agent。
6. Code Review Agent。
7. Documentation Agent。

不要求所有角色同时启动。

主 Agent 根据任务需要选择。

## B2. 双向通信

必须真实验证：

- 主 Agent 向子 Agent 派发任务。
- 子 Agent 向主 Agent 汇报进度。
- 子 Agent 向主 Agent 提交问题。
- 主 Agent 向子 Agent 追加任务。
- 子 Agent 请求其他 Agent 协助。
- Agent 之间传递 Artifact。
- Agent 之间传递结构化证据。

所有消息必须通过 Message Bus。

不允许直接修改其他 Agent 的内部状态。

## B3. 模型成本分层

普通子 Agent 默认使用低成本模型策略。

复杂设计、数学和安全审查可以使用更强模型策略。

但是：

模型选择不能改变 Agent 权限。

昂贵模型不能自动获得更高文件权限或执行权限。

本轮使用模拟 Provider 验证模型路由。

真实 Provider 接入另行授权。

## B4. 并行研发

至少选择三个相互独立的任务进行真实并行执行。

验证：

- 独立工作区。
- 并发资源预留。
- 文件冲突。
- 任务依赖。
- 消息交接。
- 取消。
- 失败恢复。
- 产物整合。

如果两个 Agent 修改同一个文件，必须通过文件所有权、版本检查或显式协调处理冲突。

禁止未经协调的并发写入。

# 六、核心工作线 C：Resident Agent

Resident Agent 是本项目最重要的长期运行角色之一。

本轮必须从简单的逻辑 Agent 原型向真实事件驱动运行机制推进。

## C1. 常驻机制

Resident Agent 应该在项目处于 ACTIVE 状态时持续运行。

但：

**常驻不等于持续调用模型，也不等于持续占用 CPU。**

建议采用：

- 事件驱动。
- 持久消息队列。
- 低成本等待。
- 按需模型调用。
- 任务状态监控。
- Agent 唤醒。
- Checkpoint。

## C2. 核心职责

Resident Agent 负责：

- 接收消息。
- 识别消息接收者。
- 分发消息。
- 检查任务状态。
- 唤醒等待中的 Agent。
- 发现无人处理的任务。
- 通知 Development Agent。
- 监控项目活动。
- 处理过期消息。
- 恢复未完成的调度工作。

Resident 不直接修改项目代码。

Resident 不擅自改变项目目标。

Resident 不拥有超出自身职责的管理权限。

## C3. 唤醒测试

必须真实验证：

1. 子 Agent 向 Resident 发送消息。
2. Resident 收到消息。
3. Resident 识别接收者。
4. Resident 唤醒对应 Agent。
5. 对应 Agent 恢复原 Task。
6. Agent 获取原 Context。
7. Agent 继续执行。
8. 结果返回发送方。

同时测试：

- 重复消息。
- 消息过期。
- Agent 不在线。
- Host 重启。
- Resident 重启。
- 唤醒失败。
- 任务取消。

## C4. 长期运行

开展有界持续运行测试。

建议先进行至少2小时的持续事件驱动测试，观察：

- 消息积压。
- CPU。
- 内存。
- SQLite。
- Artifact 增长。
- Agent 状态。
- 重复任务。
- 资源释放。

如果运行环境不支持完整长期测试，明确标记 NOT_RUN。

不得把短时间模拟演示描述为长期自治已经通过。

# 七、核心工作线 D：Background Review Agent

本轮必须验证真正独立的后台代码审查流程。

Reviewer 的主要职责是发现实现问题，而不是参与项目本体的设计决策。

## D1. 触发机制

优先支持：

- Git Commit 事件。
- Git Push 事件。
- 明确请求的代码审查任务。
- Task Contract 中规定的审查 Gate。

自动 Git Watcher 可以采用事件或受控轮询实现。

本轮不要求自动推送代码。

## D2. 审查内容

至少包括：

- 语法错误。
- 类型错误。
- Bug。
- 数值计算错误。
- 数学公式实现错误。
- 索引与边界问题。
- 并发问题。
- 状态机错误。
- 数据完整性。
- 安全问题。
- 测试覆盖。
- 实现与设计合同不一致。

可以调用成熟静态分析工具。

不必重新造轮子。

## D3. Reviewer 权限

Reviewer 默认只读。

必须验证：

- 无法修改源代码。
- 无法删除开发文件。
- 无法提交代码。
- 无法修改项目规则。
- 无法自行修改 Policy。
- 无法覆盖审计记录。

Reviewer 发现问题后：

1. 记录 Commit / Diff。
2. 记录文件和行号。
3. 记录问题描述。
4. 记录复现步骤。
5. 记录证据。
6. 发送给 Development Agent。
7. 等待开发主 Agent 决定修复任务。

不得让 Reviewer 自行修改代码来掩盖自己的审查发现。

# 八、核心工作线 E：Coordinator Agent

Coordinator 负责协调，不参与项目本体开发。

本轮需要验证：

- 多个 Agent 的状态读取。
- 多任务优先级。
- 共享资源预算。
- Agent 并发冲突。
- 任务依赖。
- 项目状态。
- 任务阻塞。
- 跨项目资源协调。

Coordinator 可以提出资源和任务调度建议。

但不能擅自：

- 修改项目目标。
- 修改项目规则。
- 修改实验合同。
- 批准高风险操作。
- 覆盖项目决策。
- 直接修改项目代码。

Coordinator 的跨项目协调必须通过可信权限和项目级接口。

# 九、Context Assembly 与长期研发记忆

这是本轮必须重点验证的基础能力。

## 9.1 上下文组成

每个 Agent 的上下文至少包括：

- 平台规则。
- 项目规则。
- Agent Role。
- Task Contract。
- 当前任务状态。
- 必要历史经历。
- 相关决策。
- 相关文件。
- 子 Agent 消息。
- 工具结果。
- Artifact 引用。

## 9.2 原始历史保护

必须继续坚持：

原始 Context Archive 不得被摘要覆盖。

允许：

- 摘要。
- 索引。
- 向量检索。
- 历史提取。
- 上下文重排。

但这些都是派生数据。

原始记录必须能够重新读取和校验。

## 9.3 Context Retrieval

当主 Agent 缺少信息时，可以派发 Retrieval Agent 读取历史。

Retrieval Agent 必须：

- 明确查询目标。
- 读取原始记录。
- 提供原始引用。
- 区分事实和推断。
- 标记缺失信息。
- 不伪造历史经历。

## 9.4 目标一致性

每次 Agent 恢复任务时，应核对：

- 原 Task。
- 项目规则版本。
- 原始决策。
- 当前文件版本。
- 当前任务状态。
- 尚未解决的问题。

规则版本发生变化时，不得静默替换旧任务的约束。

必须经过明确迁移。

# 十、Workflow Runtime 与自动质量 Gate

M1.6.1 已经建立 Project Rules Compiler 和 Gate Runtime。

本轮必须将它们真正应用于完整研发流程。

建议采用：

| Gate | 检查内容 |
|---|---|
| G0 | 项目与任务准入 |
| G1 | 规则和输入完整性 |
| G2 | 设计与任务分解 |
| G3 | 代码与测试 |
| G4 | 独立审查 |
| G5 | 交付证据 |
| G6 | 最终验收 |

每个 Gate 必须有：

- 必要输入。
- 证据引用。
- 自动检查器。
- 人工审查要求。
- 通过条件。
- 失败条件。
- NOT_RUN。
- INCONCLUSIVE。
- BYPASSED。

模型可以建议 Gate 结果。

最终结果必须由程序根据证据计算。

不能允许 Agent 直接把 Gate 状态改为 PASS。

关键安全策略不能因为关闭 Gate 就自动放行。

本轮不能只做架构测试。

8. 发现问题后通知主 Agent。
9. 主 Agent 决定修复方案。
10. Coding Agent 修复。

12. 主 Agent 整合交付。

允许 Codex 作为本轮工程执行者修复 AgentNexus 自身代码，但必须与 Pilot Agent 的实际执行记录分开。

# 十四、实施阶段

### Phase 0：基线冻结与运行条件检查

完成规则读取、源码冻结、当前资格检查。

### Phase 1：Native Harness 集成

完成五类 Agent 的统一配置和运行入口。

### Phase 2：多 Agent 并行协作

实现主 Agent、多个子 Agent、双向通信和交付整合。

### Phase 3：Resident 与 Coordinator

完成事件驱动唤醒、任务恢复和资源协调。

### Phase 4：Background Reviewer

完成只读审查和变更触发流程。

### Phase 5：Pilot 软件研发

让 Native Harness 实际完成独立软件项目。

### Phase 6：长时间运行和故障恢复

# 十八、最终验收原则

本轮不要求所有生产安全问题全部解决。

但必须证明：

1. Development Agent 能够自主规划和拆分任务。
2. 多个 Subagent 能够真正并行工作。
3. Agent 之间能够双向通信。
4. Resident 能够通过事件唤醒其他 Agent。
5. Reviewer 能够独立只读审查代码。
6. Coordinator 能够协调任务和资源。
7. Context 能够支持连续研发。
8. Workflow Gate 能够根据实际证据工作。
9. Resource Governance 能够限制预算。
10. Native Harness 能够实际完成独立软件研发任务。
11. 所有关键操作都能追溯。
12. 失败、中断和恢复不会导致未知副作用自动重试。

**最终目标不是证明五种 Agent 可以启动，而是证明它们能够作为一个协作系统完成真实的软件研发工作。**

如果只完成演示或模拟，不能标记真实自主研发 PASS。

如果模型仍然是模拟 Provider，明确说明模型层尚未完成真实联调。

如果生产 OS 隔离仍然 BLOCKED，继续限制高风险执行。
