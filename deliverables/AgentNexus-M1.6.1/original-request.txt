# 三、P0-A：两个历史 FAIL 的针对性整改

## A1. CPU 历史 FAIL

M1.6 继承的 CPU 测试仍然出现 Job 累计 29062500 ticks，最终依靠 Helper Deadline 结束。

M1.5.1 已经证明，当前 Windows JOB_TIME 不满足严格累计 CPU 预算合同。

本轮要求：

1. 核对该测试与 M1.5.1 CPU 根因报告的关系。
2. 明确它属于严格 CPU 资格失败，不能将其视为普通代码回归。
3. 保留原始预算、容差和历史 FAIL。
4. 不允许修改旧断言制造 PASS。
5. 不允许将 Helper Deadline 当成 OS CPU 限制通过。
6. 不允许将 CPU_RATE 当成累计 CPU 预算的替代品。
7. 继续确保相关严格 CPU Profile 被失败关闭机制阻断。

本轮不要求重新解决 Windows JOB_TIME 的底层机制。

如果严格 CPU 资格仍然不满足，允许该用例继续 FAIL，并在最终报告中明确标记。

可以对测试分类、失败诊断和能力资格管理进行必要整理，但不能改变原有合同。

## A2. TOCTOU Junction 历史 FAIL

M1.6 的另一个 FAIL：

原测试要求完成实际 Junction 替换，但最终 `swaps=0`。

这意味着测试没有完成预期攻击。

不能据此认定路径逃逸发生，也不能认定路径边界安全。

本轮要求：

1. 阅读原始 TOCTOU Fixture。
2. 查明 swaps=0 的具体原因。
3. 区分测试环境权限、Fixture 实现和产品代码问题。
4. 让攻击 Fixture 真正执行预期的 Junction 替换。
5. 保留原始 `swaps > 0` 要求。
6. 验证实际目录句柄边界是否阻止越权访问。
7. 验证没有读取授权工作区之外的数据。
8. 验证并发替换和异常恢复。
9. 保存攻击前后文件身份及哈希证据。

如果当前 Windows 权限不允许创建 Junction：

- 不得伪造 Junction。
- 不得通过模拟结果标记真实 OS PASS。
- 可以在独立、经过授权的测试环境完成真实测试。
- 无法完成时标记 NOT_RUN 或 INCONCLUSIVE。

特别注意：

测试没有返回外部数据，不等于攻击已经被阻断。

只有确认攻击实际发生，并且系统在真实边界上拒绝了越权操作，才能认定对应测试通过。

# 四、P0-B：持久 Storage Owner

这是本轮最重要的新功能。

M1.6 已经具备 Artifact Store、Context Archive、Audit Trail 和 Tool Gateway，但持久存储 Owner 尚未形成完整实现。

目前 LOCAL_WRITE 即使经过精确授权，也可能在操作已经发生、结果无法持久化时进入 UNKNOWN。

本轮需要解决这个问题。

## B1. Storage Owner 职责

建立统一的可信持久化所有者。

负责：

- 文件修改请求。
- 写入授权。
- 目标资源绑定。
- 文件版本管理。
- 临时文件。
- 原子发布。
- Artifact 提交。
- 审计记录。
- 写入结果核验。
- 崩溃恢复。
- Operation Reconciliation。

普通 Agent 不得直接操作 Storage Owner 的管理数据库。

所有文件写入必须通过受控接口。

## B2. 写入事务

建立清晰的文件写入状态机。

建议：

```text
REQUESTED
    |
    v
AUTHORIZED
    |
    v
WRITE_INTENT
    |
    v
TEMP_OBJECT_CREATED
    |
    v
CONTENT_WRITTEN
    |
    v
CONTENT_VERIFIED
    |
    v
PUBLISH_READY
    |
    v
PUBLISHED
    |
    v
AUDIT_ACKNOWLEDGED
```

同时定义：

- FAILED_BEFORE_PUBLISH。
- INDETERMINATE。
- RECONCILED.

具体状态可以根据现有 M1.6 协议调整。

必须区分：

文件内容已经写入临时对象、文件已经原子发布、审计已经确认。

不能把三者混为一个成功状态。

## B3. 文件写入要求

至少保证：

1. 写入之前绑定 Operation ID。
2. 精确绑定 Project、Task 和 Resource。
3. 校验原始授权。
4. 冻结写入参数。
5. 写入临时对象。
6. 计算内容 SHA256。
7. 验证文件大小。
8. 验证实际内容。
9. 在允许的文件系统语义下原子发布。
10. 记录发布前后状态。
11. 关联 Artifact。
12. 完成 Audit ACK。

对需要覆盖原文件的操作，必须明确版本和覆盖策略。

不能因为文件路径相同，就默认允许覆盖。

## B4. 崩溃恢复

必须覆盖：

- 写入前崩溃。
- 临时文件创建后崩溃。
- 写入过程中崩溃。
- 内容校验后崩溃。
- 原子发布前崩溃。
- 原子发布后 Audit ACK 前崩溃。
- ACK 后调用方收到结果前崩溃。
- 同一 Operation 重复请求。
- 两个 Agent 并发修改同一文件。
- 磁盘空间不足。
- 文件系统权限变化。
- Host 重启。

不能自动重试不确定的文件副作用。

如果文件已经发布但 ACK 丢失，必须通过文件身份、哈希、Operation ID 和发布记录进行核实。

无法核实则保持 UNKNOWN。

## B5. 存储和审计一致性

必须明确：

- Artifact Store 是实际产物存储。
- Context Archive 是 Agent 经历记录。
- Audit Trail 是操作记录。
- Decision Ledger 是正式决策。

它们不能互相替代。

需要设计可恢复的跨模块提交机制。

不能假设 SQLite 事务可以自动覆盖外部文件系统操作。

必须通过 Outbox、Intent、ACK 和 Reconciliation 解决跨存储一致性。

## B6. 并发与资源限制

继续遵守：

- 流式写入。
- 分块处理。
- 背压。
- 有界内存。
- 文件大小限制。
- 并发写入限制。
- 磁盘预算。
- 资源配额。

禁止无限累积内存。

## B7. 验收标准

至少验证：

- 文件内容正确。
- SHA256 正确。
- 原子发布行为正确。
- 重复操作不重复写入。
- 并发写入冲突被识别。
- 崩溃后能够恢复。
- UNKNOWN 不会自动释放。
- Artifact 与 Audit 能够关联。
- 历史文件不会被意外覆盖。
- 未授权文件操作被拒绝。

至少记录：

## C2. 原始上下文保护

继续坚持：

原始 Context Archive 永远不能被摘要覆盖。

摘要、索引和检索结果都是派生数据。

必须支持：

- 摘要重新生成。
- 索引重建。
- 历史重新检索。
- 分段读取。
- 内容哈希验证。
- 原始记录恢复。

## C3. Context Assembly 测试

至少测试：

- 大型历史记录。
- 超长文件。
- 多 Agent 并发读取。
- 项目规则更新。
- 旧版本 Context。

- 检索索引损坏。
- 历史记录损坏。
- 引用失效。
- 文件版本变化。
- 模型请求中途失败。

特别防止模型读取了错误版本的项目规则或文件。

## C4. 资源控制

Context Assembly 必须有：

- 最大输入大小。
- 分段读取。
- 有界内存。
- 读取背压。
- 检索上限。
- 明确截断状态。

不得静默删除重要项目规则。

上下文不足时，应明确要求补充，而不是伪造完整上下文。

# 六、P1-D：Message Bus 和 Task Scheduler 可靠性

本轮重点建立消息与任务的可靠交接。

## D1. 消息状态

明确区分：

- CREATED。
- QUEUED。
- DELIVERED。
- ACKNOWLEDGED。
- PROCESSED。
- COMPLETED。
- EXPIRED。
- CANCELLED。
- FAILED。

状态命名可以根据现有实现调整。

但必须严格区分：

消息送达、消息确认、任务执行、任务完成。

## D2. 消息可靠性

必须处理：

- 消息重复。
- 消息丢失。
- Agent 崩溃。
- Host 重启。
- 消息过期。
- 消息撤销。
- 发送方退出。
- 接收方退出。
- 并发消费。
- ACK 丢失。
- 消息顺序。
- 消息权限。

可以采用持久队列、Outbox 和幂等消费。

但不要承诺所有外部副作用都能实现 exactly-once。

对于无法确定是否执行的副作用，继续使用 UNKNOWN 和人工核实机制。

## D3. Task 与 Message 的关系

消息重投不应自动重新执行已经完成的任务。

每个 Task 必须有稳定 Task ID 和执行状态。

消息需要关联 Task ID、Operation ID 和 Correlation ID。

任务执行与消息确认必须具有明确的一致性合同。

## D4. Task Scheduler

继续验证：

- 单次任务派发。
- 依赖关系。
- 等待。
- 取消。
- 恢复。
- 显式交接。
- 资源预算。
- 并发控制。
- 崩溃恢复。

Agent 自报完成不能直接释放资源。

必须有任务产物、状态和必要证据。

## D5. 双向通信

必须真实测试：

- 主 Agent → 子 Agent。
- 子 Agent → 主 Agent。
- 子 Agent → 其他授权子 Agent。
- Reviewer → Development Agent。
- Resident → 其他 Agent。
- Coordinator → 多个项目 Agent。

消息权限由程序控制。

不能依赖提示词要求 Agent 不要给错误的接收者发送消息。

# 七、P1-E：Project Rules Compiler 与自动质量 Gate

这是本轮另一项重要工作。

我们之前已经将 Workflow Kit 的功能映射到 AgentNexus。

现在需要将项目规则从纯提示词逐步转化为机器可读和可执行的约束。

## E1. Project Rules Compiler

建立规则解析和编译模块。

输入可以包括：

- AGENTS.md。
- 项目规则文件夹。
- 项目配置。
- Feature Catalog。
- Policy Catalog。
- Task Contract。
- Workflow Contract。

输出：

- Rule Registry。
- Rule Version。
- Rule Hash。
- Rule Dependencies。
- Rule Scope。
- Machine-readable Constraints。
- Enforcement Binding。
- Gate Binding。

不能把所有自然语言内容都假装成能够自动执行。

必须区分：

1. HUMAN_READABLE：人类阅读规则。
2. MODEL_GUIDANCE：提供给模型的行为指导。
3. MACHINE_CHECKABLE：可以程序验证的条件。
4. POLICY_ENFORCED：必须由程序强制执行的规则。
5. MANUAL_REVIEW：必须人工判断的内容。

## E2. 规则版本与绑定

每个 Task 必须绑定：

- Project Rules Version。
- Rule Hash。
- Feature Epoch。
- Policy Epoch。
- Workflow Version。

规则更新后：

- 新 Task 使用新版本。
- 已运行 Task 保留原始版本。
- 需要升级规则的 Task 必须经过明确迁移。
- 不允许静默替换正在运行任务的规则。

## E3. 自动质量 Gate

建立原生 Gate Runtime。

优先支持：

- G0：任务准入。
- G1：规则和输入完整性。
- G2：设计与实施计划。
- G3：代码和测试。
- G4：独立审查。
- G5：交付证据。
- G6：最终验收。

Gate 不能只是让模型回答 PASS 或 FAIL。

每个 Gate 必须具备：

- Gate ID。
- 输入条件。
- 必需证据。
- 自动检查器。
- 人工审查条件。
- 通过条件。
- 失败条件。
- NOT_RUN 条件。
- INCONCLUSIVE 条件。
- 版本绑定。
- 审计记录。

模型可以提出 Gate 结果，但最终状态由可信 Gate Engine 根据实际证据计算。

## E4. Feature 开关

规则编译器和 Gate Runtime 必须纳入 Feature Registry。

可以独立关闭非关键辅助功能。

但关闭程序强制执行的安全策略，不得自动放开受保护能力。

关闭某个 Gate 时必须明确记录 BYPASSED，而不是伪装成 PASS。
