## 三、P0：确定真实签名环境

首先调查当前可使用的签名环境。

优先考虑：

- 与 Codex 开发环境隔离的 Windows 设备。
- 具有不同安全主体、独立密钥访问权限且代理无法控制的 Windows 会话。
- 用户实际控制的 CNG / TPM CNG 私钥。

必须核实隔离条件，而不是仅凭不同窗口或不同登录会话判断安全。

特别明确：

- 同 SID 的另一个桌面会话不构成充分隔离。
- 软件 CNG 不等于硬件隔离。
- TPM 不可导出不代表其他同 SID 进程绝对无法申请签名。
- 签名工具不联网也不自动构成可信程序。

如果当前没有符合原 Q4.2 安全合同的独立环境：

1. 明确说明缺少哪些条件。
2. 给出最小可行的操作选择。
3. 区分各方案的剩余风险。
4. 不自行降低信任标准。
5. 不继续开发新的安全平台来规避这个问题。

向用户呈现简单、明确的下一项选择，不要反复索取已经提供的信息。

## 四、P0：准备真实证书操作

复用 Q4.2 已有的：

`user-create-certificate.ps1`

和 Qualification Signer。

如果用户选择创建本地证书：

- 先检查该脚本及最终 Hash。
- 说明 SOFTWARE_CNG 与 TPM_CNG 的区别。
- 说明将修改哪个 Windows 用户的 `CurrentUser\My`。
- 说明证书和密钥的存储位置。
- 说明不可导出策略和实际调用权限。
- 说明是否需要用户交互确认。
- 明确取消及失败后的状态。

**创建实际证书和私钥必须由用户明确批准并在独立环境执行。**

Codex 不得自行创建用户签发私钥。

不得读取或导出私钥。

不得索取 PFX、私钥密码或私钥文件。

不得自动向 Root 或 Trusted Publishers 导入信任。

## 五、P0：独立证书和 Pin 核对

用户选择证书后：

1. 读取公开 DER 证书。
2. 核实 Subject、Issuer 和有效期。
3. 核实密钥算法及用途。
4. 计算 DER SHA256。
5. 让用户从独立渠道确认完整64位 Pin。
6. 保留独立核对记录。

不得将 Windows SHA1 Thumbprint 当作 DER SHA256。

不得只因为证书来自本机，就自动信任。

不得由 Codex 自行生成信任锚并自动批准。

## 六、P0：重新生成真正的部署候选

当前 Q4.2 仍然没有真实证书和最终签名，因此不能直接签署旧候选。

取得用户允许公开使用的证书和独立确认的 Pin 后，按照 Q4.2 正式流程：

1. 在目标 Windows 设备读取实际 Host Identity。
2. 核实 Machine ID、Operator SID 和预计算 Service SID。
3. 运行现有公开材料冻结工具。
4. 生成新的 Deployment ID。
5. 按现有合同生成新的 Epoch。
6. 生成新的 UTC 有效窗口。
7. 重新冻结194项安装文件。
8. 核实实际文件数量、字节数和全部 Hash。
9. 绑定 Signer、Verifier、安装器及相关配置。
10. 输出全新候选目录。

当前 Q4.2 默认准备流程使用 Epoch 5，具体以实际冻结合同为准。

候选时间窗不得超过合同允许期限。

必须坚持：

- 不覆盖旧候选。
- 不复用过期审批。
- 不替换已冻结文件。
- 不借用旧候选的 Hash。
- 不使用未经核验的依赖。
- 不修改原始历史记录。

## 七、P0：用户独立签署 Qualification Plan

本阶段由用户在独立签名环境操作。

Codex 只负责准备文件、解释操作和验证公开结果。

用户打开 Q4.2 Qualification Signer，选择第一阶段：

**Sign Qualification Plan**

必须展示：

- 目标 Host。
- Machine ID。
- Operator SID。
- Service SID。
- Epoch。
- 有效期限。
- 安装清单 Hash。
- 最终资格计划 JSON。
- 具体系统变更。
- 使用的证书及 Pin。
- 允许的合成操作。
- 全部真实权限为 false。

用户确认最终内容后，使用自己的私钥完成签署。

输出：

- `qualification-plan.json`
- `qualification-plan.p7s`
- `signing-result.json`

**这一步只批准资格计划，不批准安装。**

不得自动继续第二阶段。

不得自动执行部署。

## 八、P0：用户独立签署 Deployment Approval

第一阶段签名通过后，再进入第二阶段。

必须重新验证：

- 第一阶段 CMS。
- 证书 Pin。
- 安装清单。
- Host。
- Operator。
- Service SID。
- Epoch。
- 有效期。
- 完整资格计划。
- 最终权限范围。

随后由用户再次审阅具体的 Deployment Approval JSON。

用户独立确认并签名后输出：

- `deployment-approval.json`
- `deployment-approval.p7s`
- `signing-result.json`

继续要求：

`start_service=false`

当前阶段不能自动安装或启动 Windows Service。

## 九、P0：目标 Windows 只读验签

签署完成后，在目标 Windows 设备运行现有 Verifier。

必须核实：

1. Qualification Plan CMS。
2. Deployment Approval CMS。
3. DER SHA256 Pin。
4. 完整安装文件集合。
5. Signer / Verifier Hash。
6. Machine ID。
7. Operator SID。
8. Service SID。
9. Epoch。
10. 有效期限。
11. 权限范围。
12. 文件完整性。

预期状态：

`SIGNED_LOCAL_VERIFIED_ONLY`

验证结果必须附原始记录。

不能把该状态写成：

- DEPLOYED。
- SERVICE_RUNNING。
- OS_QUALIFIED。
- PRODUCTION_VAULT_READY。

验签不得修改系统状态。

签名完成并且验签通过后，基于最终签署文件生成新部署申请。

- 全部安装文件 Hash。
- 服务名称。
- Virtual Service Account。
- 目标安装目录。
- 数据目录。
- ACL / SDDL。
- High Pipe。
- Daily Pipe。
- Trusted Helper。
- Native Runtime。
- SCM 变更。
- 实际需要的管理员权限。

**B. 启动 Credential Service。**

**C. 使用合成凭证执行 Windows OS 资格测试。**

用户可以分别批准。

如建议一次批准某个严格限定的资格操作窗口，必须先在正式合同中明确其范围、期限、失败停止条件和回滚方式，并经用户独立批准。

不得将既有安装许可推定为启动或 OS 攻击测试许可。

- Data Egress。
- 合成端到端模型调用。
