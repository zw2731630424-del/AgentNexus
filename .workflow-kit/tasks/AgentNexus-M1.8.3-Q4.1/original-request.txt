# 三、P0：重新划分两种签发模式

当前必须明确区分：

## 3.1 LOCAL_QUALIFICATION

用途：

仅用于用户自己的 Windows 电脑进行本地资格部署和 OS 安全验证。

允许：

- 安装资格测试用 Credential Service。
- 创建必要的 Virtual Service Account。
- 设置经过批准的 ACL。
- 启动合成资格服务。
- 使用合成 Vault。
- 使用合成 Key。
- 使用 Synthetic Provider。
- 执行真实 Windows OS 攻击测试。
- 验证 UAC Helper。
- 验证 Runtime。
- 验证 High / Medium IPC。
- 验证崩溃恢复。

必须限制：

- 单一指定机器。
- 指定 Operator SID。
- 指定 Service SID。
- 固定安装清单 Hash。
- 固定资格计划 Hash。
- 明确 Epoch。
- 明确有效期。
- 明确系统变更范围。

以下必须固定为：

- real_import = false。
- live_provider = false。
- production_release = false。
- real_ledger_migration = false。

LOCAL_QUALIFICATION 不能自动升级为生产资格。

## 3.2 PRODUCTION_RELEASE

用于未来正式生产发布。

保留：

- 正式受信任签发者。
- 正式证书。
- 正式代码签名。
- 正式部署批准。
- 完整生产发布验证。

不能因为本地资格签名通过，就默认生产发布签名已经满足。

两个模式必须具有不同的签名策略、验证规则和权限边界。

# 四、P0：本地资格签发证书方案

用户目前没有商业级签发证书。

本轮研究并实现用户自主控制的本地资格签发机制。

## 4.1 本地资格证书

研究 Windows 支持的本地证书和密钥管理方案：

- Windows Certificate Store。
- CNG Key Storage Provider。
- TPM-backed Key（如果当前设备支持）。
- 不可导出私钥。
- 用户确认或交互式密钥使用保护。
- 独立离线签名工具。

优先采用：

**用户持有私钥，Codex 只接触公开证书和签名结果。**

私钥不得：

- 放入 Git 仓库。
- 放入 AgentNexus 普通配置目录。
- 放入普通 Credential Vault。
- 通过聊天发送。
- 传递给 Codex。
- 传递给 Development Agent。
- 写入日志。
- 写入部署包。
- 作为环境变量传递。

## 4.2 重要安全区别

自签名证书本身不自动可信。

只有用户明确将某个证书的 DER SHA256 Pin 作为本地资格签发信任锚，并通过独立方式确认该指纹，验证器才可以接受它。

不能因为证书是本机生成的，就自动信任。

不能让 Codex 自行生成证书，然后把它自己的证书自动加入信任列表。

不能把本地证书称为商业 CA 证书。

## 4.3 私钥使用

设计独立的本地签名流程。

用户必须能够查看待签署的具体内容：

- 安装清单 SHA256。
- 资格计划 SHA256。
- 主机标识。
- Operator SID。
- Service SID。
- Epoch。
- 有效期。
- 具体系统变更。
- 合成资格范围。
- real_import。
- live_provider。
- real_ledger_migration。

用户明确确认后才能签名。

不能只显示一个没有内容的“Approve”按钮。

优先研究要求用户交互确认的签名方式。

仅设置 NonExportable 不足以证明同 SID 恶意进程无法调用私钥。

必须如实记录本地签名密钥的安全边界和剩余风险。

如果当前 Windows 环境无法实现可信用户确认，提出离线签名方案，不得伪装成高保证签名。

# 六、P0：签名合同与部署验证器调整

现有 Q4 部署合同必须扩展为两种明确模式。

## LOCAL_QUALIFICATION 验证

必须检查：

- 证书 DER SHA256。
- 证书用途。
- 签名者身份。
- 资格计划签名。
- 部署批准签名。
- 主机身份。
- Operator SID。
- Service SID。
- 安装清单 Hash。
- 文件数量。
- 文件总字节数。
- Epoch。
- 有效期。
- 资格范围。
- 所有安全限制。

任意字段不匹配必须拒绝。

签名不完整必须拒绝。

签名过期必须拒绝。

安装清单改变必须拒绝。

## PRODUCTION_RELEASE 验证

继续执行原来的正式生产签发合同。

LOCAL_QUALIFICATION 的证书不能作为生产签发者。

不能为了兼容新模式而降低原生产验证器的要求。

## 签名类型必须分离

明确区分：

1. CMS Qualification Plan Signature。
2. CMS Deployment Approval Signature。
3. Authenticode Executable Signature。
4. Certificate DER SHA256 Pin。

这些不是同一个东西。

不能因为 CMS 审批签名通过，就宣称所有二进制都获得了 Authenticode 信任。

如果某项签名属于 Windows 部署或运行时策略要求，单独记录其目的和验证条件。

# 七、P0：部署审批必须保持独立

本地资格签发不能让 Codex 自行部署。

完整流程：

```text
Codex 完成部署候选
        |
        v
冻结文件 Hash
        |
        v
生成资格计划
        |
        v
生成部署申请
        |
        v
用户审阅实际系统变更
        |
        v
用户本地签名
        |
        v
验证签名和 Hash
        |
        v
用户单独批准实际部署
        |
        v
QUALIFICATION_ONLY 安装
```

必须明确：

**签署资格计划，不等于批准部署。**

**批准部署，不等于批准真实 Key 导入。**

**批准真实 Key 导入，不等于批准真实 Provider 请求。**

这三个授权必须独立。
