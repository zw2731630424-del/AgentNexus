# 三、A 线：Resource Governance Engine

## A1：CPU 资源合同重新设计

这是 A 线最高优先级。

不要预设继续使用 Windows JOB_TIME。

也不要预设 CPU_RATE 就能替代累计 CPU 时间预算。

必须重新定义四种独立能力：

### 1. CPU Bandwidth

限制 Worker 能够占用的 CPU 调度带宽。

例如：

- 单 Worker 最大 CPU 带宽。
- Project 总 CPU 带宽。
- Platform 总 CPU 带宽。

### 2. CPU Consumption Budget

限制累计 CPU 消耗。

例如：

- 单 Worker 累计 CPU 时间。
- 一个 Task 的 CPU 总消耗。
- 一个 Project 的 CPU 总消耗。
- 整个平台的累计 CPU 预算。

### 3. Execution Wall Deadline

限制任务实际持续时间。

必须区分：

- 任务启动时间。
- 执行时间。
- 等待时间。
- 暂停时间。
- 结束时间。

### 4. CPU Accounting

准确记录：

- User Mode CPU。
- Kernel Mode CPU。
- 主进程 CPU。
- 子进程 CPU。
- Job 累计 CPU。
- Project 累计 CPU。

明确统计来源、精度、误差和未知情况。

## A2：研究不同实现方案

对以下方案开展有针对性的技术研究：

- Windows Job Object CPU_RATE。
- Windows JOB_TIME。
- 外部可信 Supervisor。
- CPU 使用量采样。
- 进程分片执行。
- Worker 阶段性预算。
- Linux cgroup v2。
- 其他能够提供明确资源合同的执行后端。

每种方案必须回答：

1. 实际限制什么？
2. 是否为 OS 强制执行？
3. 是否覆盖子进程？
4. 是否存在检查周期？
5. 超限后多久能够停止？
6. 是否能够给出可验证的上界？
7. 是否支持多 Worker 并发？
8. 是否能够恢复？
9. 是否适合长期运行？
10. 是否符合 AgentNexus 的预算合同？

不能将监控终止冒充严格硬限制。

不能将 CPU_RATE 冒充累计 CPU 时间预算。

不能根据有限测试推导不存在的上界。

## A3：CPU 资格与失败关闭

当前 CPU 资格 FAIL 必须永久保留。

重新设计后：

- 原预算保持不变，除非单独提出新的产品合同并获得批准。
- 原始失败记录不能覆盖。
- 不得通过调整测试阈值制造 PASS。
- 不得把外部 Helper Deadline 当成 OS CPU 硬限制通过。
- 不得排除实际运行的子进程。

如果某个执行后端不能满足严格 CPU 合同：

- 该能力标记 BLOCKED。
- 不能开放对应的严格 CPU Profile。
- 可以在明确的不同产品合同下研究较弱的资源管理模式。
- 两种模式必须使用不同能力名称和资格状态。

不能让较弱模式冒充原有严格保证。

# 四、A 线：统一 Resource Governance Engine

不要把 CPU 当作孤立功能。

建立统一的资源治理系统。

## A4：资源类型

至少覆盖：

| 资源 | 管理对象 |
|---|---|
| CPU | CPU 带宽、累计消耗、执行时间 |
| RAM | Worker 内存、Project 内存、Platform 内存 |
| Disk | 工作区、临时文件、Artifact |
| Process | 最大进程数、子进程数、并发 Worker |
| I/O | 磁盘读写量、日志速率 |
| Network | 连接数量、目标范围、带宽 |
| Model | Token、请求频率、费用 |
| Time | Task 时间、Agent 生命周期 |

## A5：三级资源预算

必须明确分离：

### Worker Budget

限制单个 Agent 或 Worker 的资源使用。

### Project Budget

限制同一项目下所有 Agent 的资源总和。

### Platform Budget

限制整个 AgentNexus 平台的总资源使用。

例如：

一个 Worker 单独符合 CPU 预算，不代表多个 Worker 合起来不会耗尽服务器资源。

必须设计：

- 资源预留。
- 资源分配。
- 资源占用。
- 资源释放。
- 超额拒绝。
- 资源等待队列。
- 资源回收。
- UNKNOWN 资源隔离。

资源释放必须继续遵守 M1.2/M1.3/M1.4/M1.5 的 ExitProof 和 Reconciliation 合同。

不能仅因为 Agent 报告任务结束，就释放资源。

## A6：资源治理与 Feature Registry

Resource Governance 必须成为原生模块。

每种资源控制能力有独立 Feature ID。

例如：

- `resource.cpu.bandwidth`
- `resource.cpu.consumption`
- `resource.cpu.accounting`
- `resource.memory.limit`
- `resource.disk.quota`
- `resource.process.limit`
- `resource.io.limit`
- `resource.network.limit`
- `resource.project.budget`
- `resource.platform.budget`

实际 ID 遵守项目已有命名规则。

每个 Feature 必须定义：

- 默认状态。
- 依赖。
- 冲突。
- 关闭行为。
- 降级合同。
- 资格状态。
- 恢复方式。
- 测试映射。

关闭某项资源控制功能，不得自动放开高风险执行。

如果严格 CPU 硬限制关闭或不合格，相关严格执行 Profile 必须保持 BLOCKED。

# 五、B 线：Native Harness Core

这是本轮另一条核心研发线。

目标是从受限内核开始，建立真正的原生 Agent 运行环境。

不要只设计 Agent 的提示词和角色配置。

必须形成可执行的软件架构。

## B1：Native Agent Runtime

建立统一 Agent Runtime。

每个 Agent 必须拥有独立的：

- Agent ID。
- Agent Type。
- Runtime Instance ID。
- Project ID。
- Task ID。
- Session ID。
- Model Binding。
- Context Reference。
- Tool Capability。
- Resource Budget。
- Policy Scope。
- Lifecycle State。

逻辑身份与真实 Runtime Identity 必须分离。

Agent 不允许自行修改自己的身份、权限和资源预算。

所有状态变更通过可信 Runtime 管理。

## B2：Agent Lifecycle

建立明确生命周期：

```text
CREATED
   |
   v
INITIALIZING
   |
   v
READY
   |
   v
RUNNING
   |
   +----> WAITING
   |         |
   |         v
   +------ RESUMING
             |
             v
          RUNNING
             |
       +-----+------+
       |            |
       v            v
    STOPPING     FAILED
       |
       v
    STOPPED
```

具体状态可以根据现有 M1.5.1 合同调整。

必须覆盖：

- 创建。
- 启动。
- 唤醒。
- 暂停。
- 等待消息。
- 恢复。
- 取消。
- 终止。
- 崩溃。
- 重启恢复。

不能让 Agent 自己通过修改数据库记录改变生命周期。

必须保留审计记录。

## B3：Agent Loop

建立原生 Agent Loop。

至少包含：

1. 接收任务。
2. 读取项目规则。
3. 组装当前上下文。
4. 选择模型。
5. 发起模型请求。
6. 解析模型响应。
7. 识别工具调用。
8. 进行参数验证。
9. 进行 Feature 检查。
10. 进行 Policy 检查。
11. 申请授权。
12. 调用 Tool Gateway。
13. 收集执行结果。
14. 更新 Context Archive。
15. 更新 Task 状态。
16. 决定继续、等待、交接或结束。

所有有副作用的操作仍必须经过现有可信执行入口。

本轮不能为了让 Agent Loop 更容易实现而绕过 Policy 或 Tool Gateway。

## B4：Context Assembly

建立独立 Context Assembly 模块。

它负责根据当前 Task 组装模型请求上下文。

输入至少包括：

- 项目规则。
- Agent 角色合同。
- Task 合同。
- 最近交互。
- 当前工作状态。
- 相关历史上下文。
- 必要文件内容。
- 相关 Decision Ledger。
- 工具执行结果。
- 其他 Agent 的消息。

必须区分：

- 原始历史。
- 当前任务上下文。
- 摘要。
- 检索结果。
- 派生索引。

特别遵守：

**原始 Context Archive 必须完整保留，不能使用语义摘要覆盖原始记录。**

当上下文不足时，可以创建独立 Retrieval Agent 读取原始档案，提取相关信息。

摘要和索引必须能够重建。

上下文装配需要记录来源引用，能够追溯模型当时看到的内容。

不允许仅依靠模型自行决定哪些历史内容应该永久丢弃。

## B5：Agent Message Bus

建立原生消息总线。

支持：

- Agent → Agent。
- Parent Agent → Subagent。
- Subagent → Parent Agent。
- Agent → Coordinator。
- Reviewer → Development Agent。
- Resident Agent → Development Agent。
- Coordinator → 多个 Agent。

消息至少包含：

- Message ID。
- Sender Agent ID。
- Receiver Agent ID。
- Project ID。
- Task ID。
- Session ID。
- Message Type。
- Payload Reference。
- Priority。
- Created Time。
- Expiration。
- Correlation ID。
- Delivery State。

必须支持：

- 消息持久化。
- 去重。
- 重试规则。
- 消息确认。
- 过期消息。
- 消息撤销。
- 权限检查。
- 消息审计。

不确定的外部副作用消息不能自动重复执行。

## B6：Task Scheduler

建立统一任务调度器。

负责：

- 创建任务。
- 派发任务。
- 选择 Agent。
- 分配资源。
- 控制并发。
- 暂停任务。
- 恢复任务。
- 取消任务。
- 任务超时。
- 任务依赖。
- 任务交接。
- 失败处理。
- Checkpoint。

任务调度必须与 Resource Governance 联动。

当资源不足时：

- 不得无限创建 Worker。
- 不得无限排队占用内存。
- 不得重复创建相同任务。
- 不得绕过资源预算。
- 必须保留可恢复状态。

# 六、B 线：五类核心 Agent 的原生架构

本项目最初规划了五类核心 Agent。

本轮必须将它们正式纳入 Native Harness 的 Agent Type Registry。

## 1. Resident Agent（常驻 Agent）

职责：

- 在项目开发期间保持运行。
- 接收其他 Agent 的消息。
- 监控任务状态。
- 管理消息分发。
- 唤醒等待中的 Agent。
- 检查项目是否存在未处理任务。
- 推动项目持续开发。

常驻 Agent 不应该通过无限循环消耗大量 Token。

建议采用：

- 常驻 Runtime。
- 事件驱动。
- 持久消息队列。
- 低成本等待机制。
- 按需模型调用。

必须支持：

- 项目启动时激活。
- 项目暂停时休眠。
- 项目关闭时终止。
- Host 重启后恢复。

常驻不等于永远占用 CPU。

## 2. Development Agent（开发主 Agent）

职责：

- 规划项目。
- 分析需求。
- 制定设计。
- 拆分任务。
- 分派子 Agent。
- 整合代码。
- 处理冲突。
- 管理项目进度。
- 验收子 Agent 交付。

主 Agent 可以使用高能力、高成本模型。

但必须通过统一 Model Gateway 路由。

主 Agent 不应该把全部项目文件和所有历史塞进自己的上下文。

它负责决策和整合，具体研究工作交给子 Agent。

## 3. Development Subagent（开发子 Agent）

这是可扩展的 Agent 类型集合。

可以包含：

- Coding Agent。
- Code Review Agent。
- Research Agent。
- File Reading Agent。
- Test Agent。
- Debug Agent。
- Documentation Agent。
- Security Review Agent。
- Mathematical Review Agent。
- Scientific Review Agent。

要求：

- 由主 Agent 创建和派发。
- 拥有独立 Context。
- 拥有独立 Task。
- 使用独立资源预算。
- 使用明确文件访问范围。
- 可以与主 Agent 双向发送消息。
- 可以向其他获得授权的子 Agent 发送消息。
- 完成后提交结构化交付。

默认采用较便宜的模型。

需要更强推理能力时，可以分配更贵的模型。

模型选择不能改变权限范围。

## 4. Background Review Agent（后台审查 Agent）

职责：

- 监控提交后的代码变更。
- 监控 Push 后的代码变更。
- 自动触发独立审查。
- 查找 Bug。
- 检查数学公式和数值运算。
- 检查索引、边界、并发和状态机。
- 检查安全问题。
- 输出可复现的问题证据。

特别注意：

后台 Reviewer 主要审查代码正确性和实现问题。

不应该擅自评价项目研究方向是否有价值，也不应该随意改变项目科学目标。

Reviewer 默认只读。

Reviewer 不得自行修改开发者代码。

发现问题后通知开发主 Agent，由其决定修复任务。

审查结果必须与具体 Commit、Diff 和源码版本绑定。

## 5. Coordinator Agent（协调 Agent）

职责：

- 协调多个项目和研发任务。
- 协调多个主 Agent。
- 管理共享资源。
- 处理任务优先级。
- 处理跨项目依赖。
- 解决资源冲突。
- 提供全局进度信息。

Coordinator 不直接参与项目本体的设计和编码。

它不应擅自改变项目目标、实验合同或科学决策。

项目级决策仍由对应项目的 Development Agent 和可信管理员负责。

# 七、B 线：模型供应商与 API Key 池

本轮完成 Model Gateway 架构和必要的本地模拟实现。

不要绑定单一模型供应商。

支持未来建立独立 Provider Pool：

- OpenAI / GPT Pool。
- DeepSeek Pool。
- GLM Pool。
- 其他兼容 Provider Pool。

每个供应商拥有独立 Key Pool。

要求：

1. Key 与模型供应商绑定。
2. Key 具备独立状态。
3. 支持多个 Key。
4. 支持轮换和失效标记。
5. 支持并发额度。
6. 支持费用统计。
7. 支持请求路由。
8. 支持模型能力注册。
9. 支持供应商故障切换。
10. 支持按 Agent 类型选择模型。

API Key 必须通过 Credential Vault 管理。

不得把 Key 放进 Agent Prompt、Context Archive、普通 Audit 内容或子 Agent 消息。

本轮不读取真实 API Key，不连接真实 Provider，不产生费用。

只实现接口、模拟 Provider 和合同测试。

## 模型路由原则

例如：

| Agent | 默认模型策略 |
|---|---|
| Resident Agent | 低成本模型或事件驱动无模型等待 |
| Development Agent | 高能力模型 |
| 普通 Subagent | 低成本模型 |
| Security Reviewer | 高推理能力模型 |
| Mathematical Reviewer | 高推理能力模型 |
| Coordinator | 低成本模型，必要时升级 |

实际模型必须可配置。

模型成本不能影响 Agent 的权限和授权等级。

# 九、两条研发线共享的基础设施

# 十七、最终验收原则

M1.6 不要求完整产品一次性完成。

但必须证明两个方向都取得实际进展。

A 线：

- CPU 资源合同得到重新定义。
- 不再把不合格 JOB_TIME 当成可用能力。
- 建立真实的资源预算和核算基础。
- Worker / Project / Platform 资源管理能够运行。
- 未通过 OS 资格的硬限制仍然 BLOCKED。

B 线：

- 原生 Agent Runtime 能够创建和管理 Agent。
- Agent Loop 能够完成受限任务。
- Context Assembly 能够引用完整历史。
- Agent 之间能够双向通信。
- Task Scheduler 能够派发和恢复任务。
- 五类 Agent 有明确的运行合同。
- Model Gateway 能够通过模拟 Provider 工作。
- 所有工具调用经过统一权限和审计入口。

两条线必须共用同一套身份、权限、审计、上下文和资源体系。

**本轮最重要的结果不是让五个 Agent 同时运行，而是让 AgentNexus 真正拥有一套原生 Agent Runtime，并且具备安全、可恢复、可追踪的运行基础。**
