# AgentNexus M1.2：安全与授权闭环整改任务

## 一、你的身份与任务目标

你是 AgentNexus 项目的主开发代理 Codex，负责本轮工程实施。

当前基线：AgentNexus v0.4-m01-m1.1。

本轮任务依据：

- M1 当前完整源码。
- M1 Source Review Part 1–3。
- M1 Runtime Evidence 及其补充材料。
- Control Review（CTRL-001～CTRL-008）。
- Storage Integrity Review v3。
- M1 最终测试矩阵、交付清单及设计合同。
- 本轮独立技术审查报告。

本次不是重新设计整个 AgentNexus，也不是推翻 M1 已有成果。

核心目标：

**让 AgentNexus 从一个具有基础工具授权能力的本地内核，进一步形成具有明确强制执行边界、可恢复授权状态和可信操作裁定机制的安全执行内核。**

必须优先解决安全边界问题，而不是增加大量新功能。

## 三、P1-A：Policy Enforcement 强制执行机制

这是本轮最高优先级。

目前需要重点复核：

- PolicyEngine 的默认 RuleEvaluator。
- PolicyDefinition 的运行时校验。
- policy_ids 允许为空的问题。
- ToolDefinition 的权限声明。
- ToolContext 对 KernelStore 的直接访问。
- RuleEvaluator 注入接口。
- `requires_sandbox` 的实际安全语义。
- Policy Mode 与执行前授权检查的一致性。

### 3.1 策略配置必须严格校验

检查所有策略定义：

- 未知 Policy Level。
- 未知 Policy ID。
- 重复策略。
- 无效 enforcement_owner。
- 不合法的 modes。
- 缺少必要字段。
- 不符合策略级别约束的组合。

任何未知策略配置都必须导致拒绝启动或拒绝执行，不能默认 ALLOW。

特别检查当前默认 evaluator 中 L1、L2 和其他级别的处理逻辑。

每个级别都必须有明确的、可验证的语义。

不得因为某个策略没有实现，就自动视为允许执行。

### 3.2 工具必须声明执行能力

研究并建立最小必要的工具能力分类。

至少区分：

- 无副作用的纯计算。
- 只读操作。
- 本地写入。
- 外部副作用。
- 进程执行。

具体分类可以根据现有架构提出更合理的设计，但不得通过模糊的布尔字段代替真实权限控制。

要求：

1. 有副作用的工具必须绑定强制执行策略。
2. 不能通过传入空 policy_ids 绕过必要的安全检查。
3. 纯计算工具可以采用明确的受限例外。
4. 沙箱未验证的执行能力必须保持 BLOCKED。
5. 工具注册时验证权限声明。
6. 执行前重新验证权限、审批、Permit 和策略版本。
7. 未知执行类型默认拒绝。

### 3.3 限制工具的底层能力

重点审查 ToolContext 直接暴露 KernelStore 的问题。

普通工具不应该因为获得一个执行上下文，就同时获得完整的内核数据库操作能力。

研究是否可以改为：

- 受限的上下文访问接口。
- 受限的产物读写接口。
- 明确授权的审计接口。
- 由可信内核代为完成必要的状态变更。

不要为了形式上的封装增加大量无用抽象。

必须保证工具无法通过绕过 Gateway 的方式获得本不应具有的权限。

### 3.4 管理员与策略执行边界

检查 `ruleEvaluator`、definitions、policies 等可注入配置是否可能被非可信调用者控制。

明确区分：

- 可信 Host Bootstrap。
- 管理员能力。
- Agent 身份。
- 工具执行能力。
- 策略决策能力。

提示词约束不能代替程序级强制执行。

所有有副作用的工具操作必须经过可信策略检查、授权凭证验证和受控执行器。

默认拒绝、最小权限、不可伪造的授权凭证、作用域限制、期限限制、次数限制、审计记录及失败关闭必须落实到实际代码。

## 四、P1-B：INDETERMINATE 操作核实与恢复机制

目前系统已经具备不确定操作保护，但缺少完整的人工核实和裁定闭环。

需要独立设计并实现 Operation Reconciliation。

### 4.1 基本原则

发生以下情况时：

- 工具已经被调用，但执行结果没有成功持久化。
- 处理器超时，但无法确认外部操作是否结束。
- 进程崩溃。
- 审计结果或 ACK 丢失。
- 操作系统无法确认执行器退出。

不得自动重试。

不得自动释放仍可能产生副作用的资源锁。

不得把 INDETERMINATE 改成普通失败。

### 4.2 建立正式核实流程

研究并实现最小必要的裁定状态：

- CONFIRMED_APPLIED：有证据确认操作已经发生。
- CONFIRMED_NOT_APPLIED：有证据确认操作没有发生。
- UNKNOWN_QUARANTINED：仍无法确认，继续隔离。

具体状态命名可以调整，但必须保留上述语义。

裁定需要：

1. 可信管理员授权。
2. 关联原始 operation_id。
3. 保留原始 intent_hash。
4. 记录核实依据和证据引用。
5. 记录裁定者、时间及理由。
6. 形成不可覆盖的追加审计记录。
7. 防止重复裁定及授权重放。
8. 明确 Writer Claim 是否可以释放。

对于无法核实的操作，必须继续保持隔离。

即使确认某次操作没有发生，也不得自动重新执行。后续执行必须形成新的操作请求，并重新经过授权。

### 4.3 恢复测试

至少覆盖：

- 调用前崩溃。
- 调用后、STARTED 记录前崩溃。
- 处理器已经完成，但结果尚未持久化。
- 结果已记录，但 ACK 尚未完成。
- 执行器超时但仍在运行。
- 重复核实请求。
- 无证据的管理员裁定。
- 错误的 intent_hash。
- 仍有 UNKNOWN 操作时尝试释放资源。
- 重启后恢复原有隔离状态。

重点确保：系统不会因为恢复过程而重复执行外部副作用。

## 五、P1-C：操作系统安全边界

当前 M1 的身份机制主要是可信本地库内部的 Capability 和 Agent Identity。

它不等于操作系统身份认证。

本轮需要明确设计下一阶段的 OS 安全架构。

重点研究：

1. 独立 Host Admin 身份。
2. 独立 Worker 身份。
3. 可信 IPC 身份认证。
4. 工具执行进程隔离。
5. 文件系统访问权限。
6. 进程资源限制。
7. 真实进程树终止和退出核验。
8. Provider 凭证隔离。
9. Windows 与 Linux 的不同安全实现。

需要明确：

- 哪些能力由 AgentNexus 内核负责。
- 哪些能力必须由操作系统负责。
- 哪些能力需要独立 Worker。
- 哪些操作必须通过受控 Broker。
- 哪些能力在当前阶段仍然 BLOCKED。

本轮不要为了获得一个表面上的 OS PASS 而模拟系统权限。

没有真实操作系统证据的功能继续标记 NOT_RUN 或 BLOCKED。

不要擅自修改当前开发机器或 Ubuntu 服务器的安全配置。

## 六、P1-D：科研实验授权体系

AgentNexus 最终需要支持可信的研究工作流，但目前通用工具 Permit 不等于科研实验授权。

本轮先独立设计科研实验授权合同，不连接其他科研项目，也不启动正式实验。

重点考虑：

- 实验协议版本及 SHA256。
- 实验条件与实验臂。
- Seed 唯一身份。
- Seed 一次性 Claim。
- 同一 Seed 多臂共享训练的执行语义。
- 并行任务的原子授权。
- 失败、中断和未知状态。
- 数据产物与原始授权绑定。
- 禁止自动换 Seed 和重跑。
- 独立审计与人工裁定。

必须明确区分：

普通 Tool Permit、科研实验授权、操作系统执行权限。

三者不能混为一谈。

本轮只形成独立设计、状态机、数据合同和验收测试计划，不修改其他科研项目的实验合同。

## 八、测试和验收要求

P1-C、P1-D 完成明确的架构设计和实施边界。没有真实 OS 环境和必要授权时，不宣称其已经实现。

**Phase 4：独立复核**

对新增代码进行独立代码审查。

重点寻找：

- 策略绕过。
- 权限提升。
- 重放攻击。
- TOCTOU。
- 并发竞态。
- 崩溃恢复错误。
- 错误的成功状态。
- 未授权资源释放。

**Phase 5：最终验收**

重新运行完整测试，检查源码哈希、历史记录和交付清单。

不能只依赖旧测试结果。
